# MoveYourAss — backend: plan implementacji

> **Dla agentów:** wymagany skill: superpowers:subagent-driven-development
> albo superpowers:executing-plans. Kroki mają checkboxy (`- [ ]`).

**Cel:** backend FastAPI z panelem SQLAdmin: logowanie Google, wpisy dnia
(treningi + zdjęcia), streak tygodniowy, obserwowanie, tablica, lajki,
komentarze, push FCM, endpoint wersji aplikacji.

**Architektura:** FastAPI async + SQLAlchemy 2 (asyncpg) + Alembic na
Postgresie Supabase. Własna weryfikacja ID tokenu Google w FastAPI, po niej
własny JWT sesji (te same konta dla panelu i aplikacji). Zdjęcia w
prywatnym buckecie Supabase Storage, dostęp przez signed URL. Cała logika
dat i streaku liczona na serwerze w strefie IANA użytkownika.

**Stos:** Python 3.12 (lokalnie jest 3.12), Poetry, FastAPI, SQLAlchemy[asyncio],
asyncpg, Alembic, SQLAdmin, google-auth, PyJWT, httpx, firebase-admin,
pytest + pytest-asyncio + httpx, ruff (79 znaków, pojedyncze cudzysłowy —
jak w do-backend).

**Spec:** `docs/superpowers/specs/2026-11-01-moveyourass-design.md`

## Zasady

- **Każdy PR = osobny branch od `main`, PR do `main`, bez merge'owania
  przeze mnie.** Właściciel decyduje, co wchodzi do `main`. PR-y są
  zależne łańcuchowo (PR N bazuje na branchu PR N-1), w opisie PR podaję
  bazę, żeby dało się je mergować po kolei.
- Testy na Postgresie z docker-compose (nie SQLite): daty/strefy i
  ograniczenia unikalności mają działać jak na produkcji.
- Stałe ze spec.: bufor po północy do **01:00**; przypomnienie **20:00**
  czasu lokalnego; max **5** zdjęć na trening; próg tygodnia domyślnie **1**.

## Review Focus (przypadki, o które spec się nie potyka, a ugryzą)

1. Strefa zmienia się w trakcie tygodnia/dnia (podróż) — „dziś” i tydzień
   liczone wg aktualnej strefy, bez crasha, bez duplikatu dnia.
2. DST (zmiana czasu): dzień ma 23/25 h; bufor 00:00–01:00 nadal działa.
3. Dwa równoległe żądania dodania treningu/lajka — brak duplikatów (unique
   constraint + obsługa konfliktu zamiast 500).
4. Zablokowany użytkownik z ważnym JWT — odrzucany przy każdym żądaniu.
5. Obserwujący prywatny profil po cofnięciu akceptacji/usunięciu follow —
   natychmiast traci dostęp do zdjęć (signed URL tylko po sprawdzeniu).

## PR 2 — `feat/auth-and-users` (szkic)

- Modele: `User` (id UUID, google_sub unique, email unique, first_name,
  last_name, avatar_url, is_public bool default True, timezone IANA default
  `Europe/Warsaw`, streak_threshold int default 1, is_admin, is_blocked,
  created_at), `Role` jeśli potrzebne poza `is_admin` (rozstrzygam: start od
  flagi `is_admin` + `can_access_admin`, zgodnie ze spec „role w bazie”).
- `POST /auth/google` (ID token → weryfikacja `google-auth` → upsert usera;
  e-mail == `first_admin_email` ⇒ admin przy pierwszym logowaniu → JWT).
- `GET/PATCH /me` (profil publiczny/prywatny, strefa, próg).
- Zależność `current_user` odrzuca `is_blocked` (Review Focus #4).
- Testy: weryfikator Google podmieniany fake'iem; blokada; pierwszy admin;
  walidacja strefy IANA (`zoneinfo`).

## PR 3 — `feat/entries-and-streak` (szkic)

- Modele: `Category` (edytowalna), `DayEntry` (user, date, status ∈
  workout/rest/sick, unique(user,date)), `Workout` (entry, category,
  description, created_at).
- `app/services/days.py`: `entry_date_for(now_utc, tz) -> date` (00:00–01:00
  ⇒ poprzedni dzień; stała z settings) — testy na DST i zmianie strefy.
- `app/services/streak.py`: tydzień pn–nd w strefie, zaliczony gdy dni z
  treningiem ≥ próg, odpoczynek neutralny, choroba zamraża, trening
  nadpisuje odpoczynek. Zwraca `{streak, week_progress, week_threshold}`.
- Endpointy: `POST /entries/workouts`, `POST /entries/rest|sick`,
  `GET /entries/me`, `GET /entries/rest-hint` (próg dni bez treningu — mój
  wybór: 3 dni).
